# AI Service API Reference

v1 · 구현 전 제안 명세 · 2026-10-29

Backend가 AI 서비스를 호출하기 위한 문서다. 필드 타입·필수 여부·응답 스키마는 [openapi.json](openapi.json)에 정의한다. 이 문서는 호출 흐름과 스키마로 표현하기 어려운 정책을 설명한다. 기존 [MOM](../../../docs/mom/2026-10-26.md)의 내부 API 5개를 구체화했다.

찾은 웹페이지와 파일 등 다양한 자료의 수집·검색·근거 기반 답변을 지향하며, 활용 목적을 학습으로 제한하지 않는다. MVP 수집 대상은 공개 노션 페이지다. 웹 로더·파일 로더의 책임과 공통 출력은 [자료 로더 설계](../architecture/loader-architecture.md)를 따른다. 파일 로더와 일반 웹페이지 지원은 이후 확장한다.

## 공통 규칙

개발 Base URL은 `http://localhost:8000`, 운영은 환경에서 제공하는 HTTPS 주소다.

```http
Authorization: Bearer <AI_SERVICE_TOKEN>
Content-Type: application/json
```

- 서비스 토큰은 Backend 전용이며 사용자 세션 쿠키와 별개다. 모든 API에 필요하다.
- `userId`는 Backend가 인증한 사용자 ID다. AI는 `(userId, resourceId)` 범위로 데이터를 격리한다.
- 식별자는 UUID, 시간은 UTC RFC 3339, 본문은 UTF-8 JSON이다. 문자열 길이는 Unicode 코드 포인트 기준이다.
- 요청 본문은 최대 256 KiB다. 알 수 없는 요청 필드·명시적으로 허용하지 않은 `null`은 거부한다. 응답의 추가 필드는 무시한다.
- 선택 UUID 헤더 `X-Request-Id`는 추적용이다. 생략·잘못된 값이면 서버가 새 ID를 발급하며, 잘못된 값에는 `400`을 반환한다. 응답에 실제 사용한 ID와 `Cache-Control: no-store`를 포함한다.
- GET·DELETE는 본문이 없다. query는 명세된 `userId`만 허용한다. POST 입력은 JSON 본문으로 전달한다.

| Method | Path                                                    | 성공                            |
| ------ | ------------------------------------------------------- | ------------------------------- |
| POST   | `/internal/v1/ingestions`                             | 신규 `202`, 동일 작업 `200` |
| GET    | `/internal/v1/ingestions/{jobId}?userId={userId}`     | `200`                         |
| DELETE | `/internal/v1/resources/{resourceId}?userId={userId}` | `204`                         |
| POST   | `/internal/v1/retrieval/search`                       | `200`                         |
| POST   | `/internal/v1/answers`                                | `200`                         |

아래 JSON 예제는 요청 본문이다. 예제 식별자는 실제 Backend 식별자로 교체한다.

## 1. 자료 수집 및 색인

`POST /internal/v1/ingestions`

```json
{
  "jobId": "22222222-2222-4222-8222-222222222222",
  "userId": "11111111-1111-4111-8111-111111111111",
  "resourceId": "33333333-3333-4333-8333-333333333333",
  "source": { "type": "URL", "url": "https://example.notion.site/reference-0123456789abcdef0123456789abcdef" }
}
```

모든 필드는 필수다. Backend가 `jobId`를 발급하고 AI는 작업을 영속 접수한 후 `202`를 반환한다. 응답은 `IngestionJob`이며 `Location`에 작업 조회 경로, `Retry-After: 2`를 포함한다. 신규 접수 응답의 상태는 `QUEUED`다.

**중복·재시도:** 같은 `jobId`와 입력을 보내면 현재 작업을 `200`으로 반환하고 재실행하지 않는다. 객체 키 순서와 UUID 대소문자는 무시하고 URL 문자열은 정확히 비교한다. 다른 입력에 같은 ID를 쓰면 `409 JOB_ID_CONFLICT`다. 실패한 작업의 재실행은 새 `jobId`로 요청한다.

같은 자료에 다른 작업이 진행 중이면 `INGESTION_IN_PROGRESS`, 이미 성공했으면 `RESOURCE_ALREADY_INDEXED`, 삭제되었으면 `RESOURCE_DELETED`로 `409`를 반환한다. 기존 작업의 정확한 중복 판정을 먼저 하므로 삭제 이후에도 과거 작업을 반환할 수 있지만 재실행하지 않는다. 자료 URL은 최초 접수 후 변경할 수 없으며 다른 URL로 재시도하면 `400`이다.

| 수집 항목 | 지원·제한                                                                  |
| --------- | --------------------------------------------------------------------------- |
| 대상      | 로그인이나 별도 접근 권한 없이 열람 가능한 공개 노션 페이지 한 개 |
| URL       | HTTP(S), 최대 2,048자. 사용자 정보·fragment·비표준 포트 금지              |
| 콘텐츠    | `text/html`, `application/xhtml+xml`만 지원                             |
| 수집 방식 | 웹 로더에서 공개 웹페이지를 스크래핑한다. HTML 직접 추출을 우선하고 본문 확보에 필요하면 브라우저 렌더링을 사용한다. 노션 공식 API나 사용자 계정 연결은 요구하지 않는다. |
| 범위      | 입력한 한 페이지의 본문 텍스트와 문서 구조. 렌더링에 필요한 스크립트·스타일·데이터 요청은 허용하되 하위 페이지·외부 링크를 재귀 수집하지 않는다. |
| 미지원    | 일반 웹페이지, 로그인·사용자 쿠키 전달, 파일 입력, 첨부파일 본문, 이미지 OCR, 외부 임베드 본문 |
| 한도      | 최초 HTML은 압축 해제 후 최대 5 MiB, 추출 본문은 최대 200,000자. 브라우저 총 전송량·요청 수·메모리 한도는 노션 수집 검증 후 구현 전에 확정한다. |
| 시간      | 직접 수집은 15초/시도. 브라우저 렌더링은 별도의 유한한 기한을 구현 전에 확정하며, 두 경로 모두 전체 작업 기한 10분 안에 종료한다. |
| 주소 검사 | 공개 인터넷 주소만 허용. 문서 이동·리다이렉트 최대 3회. 최초 요청·이동·렌더링 하위 요청마다 목적지와 실제 연결 주소를 검사한다. |

MVP는 `notion.site`, `notion.so` 및 각 하위 도메인의 공개 페이지 URL을 대상으로 한다. 호스트는 URL 파싱 후 도메인 경계로 판정하며, 사용자 지정 도메인은 이후 확장한다. 최종 페이지가 공개 노션 문서인지 확인한다. 지원 대상 외 웹페이지는 비동기 작업의 `FAILED / UNSUPPORTED_SOURCE`로 반환한다. 일반 웹사이트를 수집할 수 있다는 의미로 해석하지 않는다.

웹 로더의 노션 추출 결과는 공통 문서 형식으로 변환하고 이후 청킹·임베딩·색인 흐름을 공유한다. 로딩·로그인·접근 제한 화면만 가져왔거나 본문을 확보하지 못한 경우 성공으로 처리하지 않는다. 브라우저 세부 한도는 아직 확정되지 않은 설계 항목이며, 공개 노션의 본문·표·토글 추출을 검증한 후 정한다.

접수 시 URL 문법 오류는 `400`이다. 접수 후 주소 차단·접근·추출·임베딩 실패는 HTTP 접수 오류 대신 작업의 `FAILED`로 조회한다. 원본 접근 실패에 대한 오류 코드는 OpenAPI의 `JobError`에 있다. 원본 HTTP 401/403 또는 로그인·접근 제한 화면은 `SOURCE_ACCESS_DENIED`, 404/410은 `SOURCE_NOT_FOUND`, 그 외 HTTP·DNS·연결 실패는 `SOURCE_FETCH_FAILED`다. 200 응답도 본문 수집 성공을 의미하지 않는다. 수집·렌더링 기한 초과는 `SOURCE_FETCH_TIMEOUT`, charset 해석·본문 추출 실패는 `CONTENT_EXTRACTION_FAILED`다. 정상적으로 추출한 문서에 색인할 텍스트가 없으면 `EMPTY_CONTENT`다. `UNSUPPORTED_SOURCE`는 `retryable: false`로 반환한다.

### 작업 조회

`GET /internal/v1/ingestions/{jobId}?userId={userId}`

응답 `IngestionJob`은 식별자, 상태, `createdAt`, `startedAt`, `completedAt`, `result`, `error`를 포함한다. 처음 실행 전 `startedAt`, 종료 전 `completedAt`은 `null`이다.

| AI 작업 상태 | 의미                    | Backend 자료 상태 |
| ------------ | ----------------------- | ----------------- |
| QUEUED       | 접수·대기              | REGISTERED        |
| EXTRACTING   | 수집·추출              | EXTRACTING        |
| INDEXING     | 청킹·임베딩·색인 작성 | INDEXING          |
| SUCCEEDED    | 전체 색인이 검색 가능   | READY             |
| FAILED       | 실패 종료               | FAILED            |
| CANCELLED    | 자료 삭제로 중단        | DELETED           |

정상 전이는 `QUEUED → EXTRACTING → INDEXING → SUCCEEDED`이며 각 진행 상태에서 `FAILED` 또는 `CANCELLED`로 종료할 수 있다. 종료 상태는 바뀌지 않는다. 부분 색인은 검색에 공개하지 않는다.

- 성공 시 `result`에 `title`, `canonicalUrl`, `chunkCount`, `indexedAt`을 반환하고 `error`는 `null`이다. 제목은 없으면 `null`, URL은 실제 수집한 최종 URL이다.
- 실패·취소 시 `error`에 `code`, `message`, `retryable`을 반환하고 `result`는 `null`이다. 진행 중에는 둘 다 `null`이다. 취소 오류는 `RESOURCE_DELETED`다.
- 진행 중 응답은 `Retry-After: 2`를 포함한다. Backend는 2초부터 최대 10초 간격으로 폴링한다.
- 접수부터 대기 포함 10분 안에 종료한다. 초과하면 `FAILED / INGESTION_TIMEOUT`이다. AI는 재시작 후 미완료 작업을 복구하고 원래 기한을 유지한다. 단계 내부의 일시 실패는 최대 3회 재시도하되 전체 기한을 넘지 않는다.
- 종료 결과는 30일 보존한다. 이후 조회·정확한 중복 POST는 `404 JOB_NOT_FOUND`다. 최소 중복 방지 정보는 유지하므로 오래된 ID로 재실행하지 않는다.
- 없는 작업·소유자 불일치는 `404 JOB_NOT_FOUND`다. Backend는 현재 작업 ID에 해당하는 결과만 반영하고, 삭제 자료를 과거 성공 결과로 되살리지 않는다.

## 2. 자료 검색

`POST /internal/v1/retrieval/search`

```json
{
  "userId": "11111111-1111-4111-8111-111111111111",
  "query": "RAG에서 검색의 역할은 무엇인가요?",
  "resourceIds": ["33333333-3333-4333-8333-333333333333"],
  "topK": 5
}
```

`userId`, `query`, `resourceIds`는 필수다. 질문은 1~8,000자이며 공백만 있는 값은 금지한다. 자료 목록은 최대 100개이며 중복은 금지한다. `topK`는 기본 5, 범위 1~20이다.

응답은 `{"results": [...]}`다. 각 결과는 `resourceId`, `chunkId`, `title`, `content`, `rank`, `locator`를 갖는다. 관련도 순으로 최대 `topK`개를 반환하며 부족하면 더 적게 반환한다. 순위는 1부터 연속되고 원시 유사도 점수·페이지네이션은 제공하지 않는다. 결과가 없으면 `200`과 빈 배열이다.

**검색 범위:** Backend가 소유권과 READY 상태를 검증한 자료만 보낸다. `resourceIds` 생략은 `400`, `[]`는 빈 검색 범위다. AI도 사용자·자료·색인 공개 상태를 검색 필터로 적용한다. 지정 자료 중 하나라도 없거나 삭제되었으면 `404 RESOURCE_NOT_FOUND`, 모두 존재하지만 준비되지 않은 자료가 있으면 `409 RESOURCE_NOT_READY`다. 부분 결과를 조용히 반환하지 않는다.

## 3. 답변 생성

`POST /internal/v1/answers`

```json
{
  "userId": "11111111-1111-4111-8111-111111111111",
  "mode": "RESOURCE",
  "message": "RAG에서 검색의 역할을 설명해줘.",
  "history": [],
  "resourceIds": ["33333333-3333-4333-8333-333333333333"]
}
```

`userId`, `mode`, `message`는 필수다. `GENERAL`은 자료 검색 없이 답하며 `resourceIds`를 보내면 `400`이다. `RESOURCE`는 명시한 자료에서 검색하며 검색 API와 동일한 범위 검증을 적용한다. 현재 요청의 자료 범위만 사용하고 과거 이력의 자료 범위를 상속하지 않는다.

| 입력      | 규칙                                                                       |
| --------- | -------------------------------------------------------------------------- |
| message   | 현재 질문, 1~8,000자, 공백만 있는 값 금지                                  |
| history   | 기본 `[]`, 최대 20개. 각 항목은 `role`, `content`                    |
| role      | USER / ASSISTANT만 허용                                                    |
| content   | 항목당 1~8,000자, 공백만 있는 값 금지                                      |
| 이력 순서 | 오래된 순의 완료된 USER/ASSISTANT 쌍. 현재 질문·실패·생성 중 메시지 제외 |
| 전체 입력 | message와 history 텍스트 합계 최대 32,000자                                |

입력 예산이 부족하면 오래된 이력 쌍부터 제외하며 현재 질문은 자르지 않는다. 질문만으로 예산을 넘으면 `400 CONTEXT_LIMIT_EXCEEDED`다. MVP에서는 이력 요약·웹 검색·스트리밍을 제공하지 않는다. 답변은 기본 한국어이며 명시적인 언어 요청을 따른다.

### 응답 예제

```json
{
  "answerId": "55555555-5555-4555-8555-555555555555",
  "mode": "RESOURCE",
  "status": "ANSWERED",
  "content": "검색한 자료를 근거로 답변을 생성합니다.[1]",
  "citations": [
    {
      "citationId": "1",
      "resourceId": "33333333-3333-4333-8333-333333333333",
      "chunkId": "44444444-4444-4444-8444-444444444444",
      "title": "프로젝트 참고 자료",
      "excerpt": "RAG는 검색한 자료를 근거로 답변을 생성한다.",
      "locator": { "type": "URL", "url": "https://example.notion.site/reference-0123456789abcdef0123456789abcdef", "section": null }
    }
  ],
  "context": { "historyMessagesUsed": 0, "historyTruncated": false },
  "createdAt": "2026-10-28T06:01:00Z"
}
```

| status                | 의미                                     | 출처                                |
| --------------------- | ---------------------------------------- | ----------------------------------- |
| ANSWERED              | 답변 생성 완료                           | GENERAL은 없음, RESOURCE는 1개 이상 |
| INSUFFICIENT_EVIDENCE | RESOURCE에서 질문을 뒷받침할 근거가 부족 | 없음                                |
| REFUSED               | 모델·서비스 안전 정책에 따른 거절       | 없음                                |

모두 HTTP `200`이다. 근거 부족과 장애는 구분하며 시스템 장애를 정상 결과로 숨기지 않는다. RESOURCE의 빈 자료 목록은 검색·LLM 호출 없이 `INSUFFICIENT_EVIDENCE`를 반환하고 이력 사용 수는 0, 절단 여부는 false다. 자료 근거를 문맥에 넣을 수 없는 경우도 근거 부족으로 처리한다. 일반 지식으로 자동 전환하지 않으며 자료가 충돌하면 출처와 함께 충돌을 설명한다.

`content`는 최대 16,000자 Markdown이며 초과 시 문장 경계에서 축약하고 참조를 맞춘다. 출처는 최대 10개다. 본문의 `[1]`은 출처의 `citationId: "1"`과 대응하고 ID는 1부터 연속된다. 같은 청크는 같은 ID를 사용하며 본문 참조와 출처가 양방향으로 일치해야 한다. `excerpt`는 실제 청크에 존재하는 1~1,000자 연속 텍스트다. 구조 검증·복구 실패는 `502 AI_PROVIDER_ERROR`다.

검색 결과·출처의 `locator`는 `type: URL`, 최종 원문 `url`, 절 제목 `section`으로 구성한다. 제목·절 제목은 최대 500자이며 없으면 `null`이다. URL은 최대 2,048자, 검색 청크 content는 최대 8,000자다. 정확한 문단 이동과 현재 웹페이지의 과거 내용 일치는 보장하지 않는다.

AI는 대화를 저장하지 않는다. Backend가 답변·출처 스냅샷을 함께 저장하고 안전한 Markdown으로 표시한다. `answerId`는 생성 결과 식별자이며 조회 API·멱등성 기능은 없다. Backend는 사용자별 활성 생성을 하나로 제한하고 대화 초기화 전의 늦은 답변을 버린다.

## 4. 자료 삭제

`DELETE /internal/v1/resources/{resourceId}?userId={userId}`

Backend는 소유권 검증 후 자료를 먼저 검색 대상에서 제외한다. AI는 삭제 표시를 영속 기록하고 온라인 추출 콘텐츠·청크·임베딩·작업용 임시 콘텐츠 정리를 완료하면 본문 없이 `204`를 반환한다. 없는 자료·반복 삭제도 `204`이며 다른 사용자의 데이터는 변경하지 않는다.

삭제 표시는 늦게 도착한 색인 요청과 진행 중인 워커의 후속 저장을 차단한다. 진행 작업은 `CANCELLED`로 종료한다. 삭제 표시 후 정리 실패는 `503`, 기한 초과는 `504`이며 표시를 되돌리지 않는다. Backend는 `204`까지 같은 DELETE를 재시도한다. 삭제 표시 자체에 실패하면 AI 측 제외를 보장할 수 없으므로 Backend의 제외 상태를 유지한다.

검색·생성 중 요청 범위의 자료가 삭제되면 응답 직전 검증에서 `409 RESOURCE_SCOPE_CHANGED`로 종료한다. 이미 AI를 떠난 응답은 회수할 수 없어 Backend도 저장·반환 전에 재검증한다. 작업 메타데이터·최소 중복 방지 정보와 삭제 표시는 남기며 과거 메시지·출처는 이 API가 지우지 않는다.

## 5. 오류와 재시도

```json
{
  "error": { "code": "RESOURCE_NOT_READY", "message": "Requested resources are not ready.", "retryable": false, "details": [] },
  "requestId": "77777777-7777-4777-8777-777777777777"
}
```

`code`로 분기하고 `message`를 사용자에게 그대로 표시하지 않는다. `details`는 `{field, reason}` 배열이며 없으면 `[]`다. 전체 오류 코드는 OpenAPI의 `ErrorResponse`, 비동기 처리 오류는 `JobError`에 있다.

| HTTP            | 분류                                       |
| --------------- | ------------------------------------------ |
| 400 / 413 / 415 | 입력·본문 크기·콘텐츠 형식 오류          |
| 401 / 403       | 서비스 인증·호출 권한 오류                |
| 404 / 409       | 자료·작업 없음, 상태·중복 충돌           |
| 429             | 처리 용량 초과. Retry-After 제공           |
| 502 / 503 / 504 | 공급자 오류 / 서비스 불가 / 처리 기한 초과 |
| 500             | 분류되지 않은 서버 오류                    |

| 호출            | AI 처리 기한 | Backend 권장 읽기 타임아웃 |
| --------------- | ------------ | -------------------------- |
| 색인 접수·조회 | 5초          | 10초                       |
| 삭제            | 10초         | 15초                       |
| 검색            | 15초         | 20초                       |
| 답변 생성       | 60초         | 65초                       |

연결 타임아웃은 3초를 권장한다. 네트워크 오류·429·502·503·504는 답변 생성 외에는 최대 3회 자동 재시도한다. `Retry-After`를 우선하고 없으면 1초부터 지수 증가·무작위 지연을 적용해 최대 30초 간격으로 시도한다. 이후 색인 전달·삭제는 미완료 기록을 남겨 복구한다. 다른 오류는 원인 해결 전에 자동 재시도하지 않는다.

답변 생성은 기본 자동 재시도를 하지 않는다. 타임아웃 뒤 재호출은 추가 비용·다른 답변을 만들 수 있다. `retryable`과 요청 추적 ID는 멱등성을 보장하지 않으며 메시지 중복 저장은 Backend가 방지한다. 작업 오류의 `retryable`은 새 작업 ID로 재시도할 수 있다는 뜻이다.

## 정책을 이렇게 정한 이유

- **독립 서비스:** Backend는 사용자·자료·대화를, AI는 실행 작업·검색 데이터를 소유한다. 각자의 DB에 직접 접근하지 않아 내부 구현을 바꿔도 API 계약을 유지할 수 있다.
- **복구 가능한 색인:** Backend 발급 작업 ID와 영속 접수로 응답 유실을 복구한다. Backend도 전달할 요청을 영속 기록하고 AI 상태를 조회해 동기화한다.
- **명시적인 검색 범위:** 빈 목록을 전체 검색으로 해석하지 않고 자료 범위·권한을 서버에서 검증해 의도치 않은 검색을 막는다.
- **불변 자료:** 성공한 색인의 갱신·삭제 후 재등록은 새 자료 ID를 사용한다. MVP에서 버전 교체와 과거 출처 관리의 복잡도를 줄인다.
- **근거 중심 답변:** 근거가 없으면 확인할 수 없다고 반환한다. 출처는 실제 검색 데이터로 조립하며 의미적 근거 부합성은 별도 품질 평가가 필요하다.
- **수집·생성 경계:** 공개 주소만 수집하고 문서 속 지시는 신뢰하지 않는다. 임의 URL 호출·코드 실행 도구와 비밀 자격 증명을 모델에 제공하지 않는다.
- **최소 보존:** 질문·답변·원문·토큰·URL query는 기본 운영 로그에서 제외한다. 운영 로그·종료 작업·백업은 30일 보존하고 복원 시 삭제 표시를 먼저 재적용한다. 최소 삭제·중복 방지 정보는 유지한다. 외부 모델 공급자의 보존 조건은 실제 계정 설정으로 확인한다.

이 정책과 수치 한도는 MVP 기본안이다. 호출자에게 영향을 주는 변경은 조율하고 호환되지 않는 변경은 새 API 버전으로 제공한다.
